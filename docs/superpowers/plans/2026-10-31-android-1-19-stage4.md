# Android App 1.19 — Stage 4 (Inspections, Templates, Client Sharing) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On the phone, people fill in their project's inspections with no signal (answers, readings, finger signatures, follow-up tasks, finish — kept on the phone and sent in order when the signal is back), use templates (new project / new task from one, Save as template), and share a project with its client (Share with client panel, Show to client on tasks, minutes and inspection reports) — the website 1.19's features, its words and its rules.

**Architecture:** The website's inspection outbox (`lib/inspection-outbox.ts`) is copied into the app with a drift test that allows exactly three named edits; it keeps its synchronous `DraftStorage`, which the app backs with an in-memory mirror of AsyncStorage (hydrated at start, written through per key), one outbox per signed-in person whose requests go only with that person's session (`api.forUser`). It stays separate from the app's offline queue (`lib/sync-queue`) exactly as the website keeps it separate from its own offline queue: it has its own conflict rules (edit times, signed answers, finish ids) that a FIFO of HTTP writes cannot express. Server and website logic is copied into `src/lib/*.ts` with drift tests; screens are checked by source text. Two lanes: inspections (Lane I) and the task/project surfaces (Lane S: templates, client sharing, checks on cards/panel/form).

**Tech Stack:** Expo SDK 51, React Native 0.74.5 (`PanResponder`, `AppState`), react-native-svg 15.2.0 (already installed in Stage 1: the pad draws with it and `Svg.toDataURL` makes the PNG), React Navigation 6, TanStack Query 5, AsyncStorage 1.23.1, vitest 2 + esbuild. No new package.

**Spec:** `docs/superpowers/specs/2026-10-31-android-app-parity-1-19-design.md` §3 "Stage 4", owner decisions 2 and 5; `docs/superpowers/specs/2026-10-31-android-app-parity-1-19-gap.md`. ## Review Focus

1. Answers, a follow-up request and a finish made with no signal, then Android closes the app: on the next start they are all there and, once online, go once and in order (answers → follow-ups → finish); a reply lost on the way makes no second follow-up task → Task 4 `draft-storage.test.ts` "survive the app being closed…", "a follow-up request whose reply was lost…".
2. A shared phone: person A answers offline, their session ends, person B signs in — B never sees, counts or sends A's inspection (A's requests go only with A's session); a deliberate sign-out asks first and removes only that person's records, the lock screen and an expired session keep them → Task 5 `inspection-outboxes.test.ts`, `sign-out.test.ts`.
3. A reading outside its limits (typed "162.5" on 0–150 psi, Arabic digits, a comma) is Fail on the phone whatever was tapped, and the server's own rules module gives the same result → Task 1 `inspection-copies.test.ts`, Task 7 `inspection-item.test.ts`.
4. A signature drawn offline is kept with the waiting finish and uploaded with it as the PNG data URL the server reads (Android's Base64 line breaks removed) → Task 4 restart test, Task 8 `signature-ink.test.ts`.
5. Turning "Show to client" on for minutes (and an inspection report) shows the website's preview first; nothing is made visible until "Show to client" in the preview is tapped; turning it off hides at once → Task 2 `clientSwitchStep`, Task 19 and Task 11 source tests.
6. The phone's storage for inspections is full, or one record is too long for Android to read back: the change stays in the app, the banner says "This phone’s storage is full…", nothing is lost silently → Task 4 "a record past what Android can read back…".
